# Golden Set — модулі продукту

> Рейтинг описаний окремо, у [`RATING.md`](RATING.md) — він база для всього нижче.
> Тут: що саме будуємо, які дані під цим лежать і які рішення вже прийняті.

---

## 0. Чесна оцінка обсягу

Список нижче — це не «додаток», а **платформа з маркетплейсом і платежами**: бронювання з грошима,
абонементи, лояльність, тренери з виплатами, магазин. Для орієнтиру: бронювання + оплати + абонементи
+ кешбек — це приблизно стільки ж роботи, скільки весь теперішній додаток разом із рейтингом.

Це не заперечення — це попередження про порядок величин і причина, чому §10 пропонує послідовність
запуску, а не «зробимо все й покажемо».

## 1. 🎾 Пошук партнерів

Уже частково спроєктовано (`game_requests`). Ключове — **підбір за рівнем**, і саме тут рейтинг
починає окупатися.

- фільтри: місто/район, рівень ±0.5, час, покриття, одиночка/пара, стать, вік;
- «відкрита заявка»: гравець публікує слот («шукаю суперника, субота 10:00, Хуст, рівень 3.0–4.0»),
  інші приєднуються;
- зворотний бік — «швидкий підбір»: показуємо 5 гравців поблизу з найближчим рейтингом і вільним
  часом;
- після гри обидва підтверджують рахунок → матч іде в рейтинг.

```
game_requests    id, author_id, court_id, starts_at, duration_min, game_type(single|double),
                 level_min, level_max, slots, status(open|full|done|cancelled), note
request_players  request_id, profile_id, status(joined|left), joined_at
```

**Показник надійності гравця** (окремо від рейтингу): відсоток ігор, на які людина прийшла вчасно й
не скасувала в останній момент. Без нього пошук партнерів мертвий — одна людина, яка тричі не
прийшла, вбиває довіру до всього розділу.

## 2. 🏟 Бронювання кортів + абонементи + кешбек

### Бронювання

```
courts           id, club_id, name, surface, indoor, lights, city, geo, photos[]
court_slots      court_id, weekday, time_from, time_to, price, currency  -- сітка цін
bookings         id, court_id, profile_id, starts_at, ends_at, price, status
                 (pending|paid|confirmed|cancelled|no_show), payment_id, created_at
clubs            id, name, city, address, phone, payout_details, commission_pct
```

Правила, які треба вирішити з клубами **до** коду: вікно скасування без штрафу, хто несе комісію
платіжки, що робить no-show.

### Абонементи

```
subscriptions      id, club_id, name, kind(hours|visits|unlimited), amount, period_days, price
user_subscriptions id, profile_id, subscription_id, balance_left, valid_until, status
```

Три типи, які покривають реальну практику клубів: пакет годин, пакет візитів, безліміт на період.
Бронювання спершу списує з абонемента, і лише потім іде в оплату.

### Кешбек і бали лояльності

```
loyalty_ledger   id, profile_id, kind(earn|spend|expire|adjust), points, source(booking|lesson|shop),
                 ref_id, balance_after, expires_at, created_at
```

**Тільки журнал, ніякого поля `balance` в профілі.** Баланс — це сума журналу. Інакше перший же збій
у розрахунку створить гроші з повітря, і знайти, звідки вони взялися, буде неможливо.

Стартові правила: 5% від суми бронювання балами, 1 бал = 1 грн, балами можна оплатити до 50%
наступного бронювання, бали згорають через 12 місяців.

## 3. 🏆 Турніри

Механіка рейтингу і норми — в [`RATING.md` §6](RATING.md). Тут — сам модуль.

```
tournaments       id, club_id, name, category(GS-100|250|500|1000|Finals),
                  format(single_elim|round_robin|groups_playoff), starts_at, ends_at,
                  entry_fee, max_players, level_min, level_max, organizer_id, status, cover_url
tourn_entries     tournament_id, profile_id, seed_no, status(pending|paid|confirmed|withdrawn)
tourn_rounds      tournament_id, round_no, name
tourn_slots       round_id, slot_no, player_a, player_b, match_id, winner_id
```

- посів — за GS Points на момент закриття реєстрації;
- сітка генерується Edge Function (стандартний посів 1 vs N, 2 vs N−1), результати матчів
  автоматично рухають переможця далі;
- організатор — роль, а не окремий тип акаунта: клуб або гравець з правом створювати турніри;
- оплата участі — через той самий платіжний модуль (§9).

## 4. 👨‍🏫 Тренери

```
coach_profiles   profile_id, bio, experience_years, certifications[], languages[],
                 hourly_rate, currency, is_verified, payout_details
coach_services   id, coach_id, kind(individual|pair|group|kids), duration_min, price
coach_slots      coach_id, weekday, time_from, time_to           -- регулярна доступність
lessons          id, coach_id, student_id, service_id, court_id, starts_at, price,
                 status(pending|paid|done|cancelled), payment_id
coach_reviews    lesson_id, author_id, rating(1..5), text, created_at
```

- тренер бронює корт разом із уроком — це одна операція для учня, дві сутності всередині;
- верифікація тренера обов'язкова (сертифікат або підтвердження клубу), інакше розділ швидко
  заповниться самопроголошеними;
- тренер може підтверджувати рівень гравця (`level_source = verified`) — це вже закладено в базі.

## 5. 💬 Чати

Три різні речі, які легко сплутати. Одна таблиця тредів із типом — не три окремі підсистеми:

```
threads         id, kind(direct|match|tournament|club|global), ref_id, created_at
thread_members  thread_id, profile_id, role(member|moderator), last_read_at, muted
messages        id, thread_id, author_id, body, attachment_url, reply_to, created_at, deleted_at
```

| Тип | Хто всередині | Навіщо |
|---|---|---|
| `direct` | двоє | домовитись про гру |
| `match` | учасники конкретного матчу | узгодити час, корт, підтвердити рахунок |
| `tournament` | усі учасники турніру | оголошення організатора, зміни розкладу |
| `club` | відвідувачі клубу | локальна спільнота |
| `global` | усі | загальний чат застосунку |

Реалізація — Supabase Realtime. **Модерація обов'язкова з першого дня**: скарга, блокування
користувача, видалення повідомлення. Без цього застосунок із загальним чатом просто не пройде ревʼю
App Store — це прямо прописана вимога до застосунків з користувацьким контентом.

## 7. 🛒 Магазин спорядження

**Поки що заглушка** — екран «Скоро» з формою «повідомити, коли запрацює». Це правильне рішення:
магазин — це склад, доставка, повернення й податки, тобто окремий бізнес, а не екран.

Але одну річ варто зробити одразу — **каталог моделей ракеток і струн** (§8). Він потрібен статистиці
незалежно від магазину, і коли магазин зʼявиться, товари підвʼяжуться до вже наповненого каталогу.

## 8. 📊 Профіль і статистика

Найнедооціненіший модуль: саме він дає причину повертатися в застосунок між іграми.

### Спорядження

```
equipment_catalog  id, kind(racquet|string|shoes), brand, model, year, specs jsonb
user_equipment     id, profile_id, catalog_id, nickname, is_primary,
                   string_model, tension_kg, weight_g, grip_size, since, retired_at
match_equipment    match_id, profile_id, user_equipment_id
```

Кожен матч може посилатися на ракетку, якою грали. Звідси природно виростає те, чого немає більше
ніде: **статистика по ракетці** — відсоток перемог, середня дельта рейтингу, улюблене покриття. І
далі агрегат по всій спільноті: «гравці рівня 4.0 найчастіше грають Wilson Blade, середній
натяг 23 кг».

### Статистика гравця

- усі матчі: суперник, рахунок, корт, покриття, дата, ракетка, дельта рейтингу;
- графік рейтингу в часі, зі **стартовим рейтингом як першою точкою** (див. `RATING.md` §2);
- баланс перемог/поразок: загальний, за покриттям, за рівнем суперника, за форматом;
- найкраща перемога (суперник з найвищим рейтингом);
- історія по конкретному супернику: «з Максимом 4:7»;
- ачівменти: golden set, «бейгл» 6:0, серія перемог, перемога над вищим рейтингом.

Профіль публічний: інший гравець заходить і бачить рівень, статистику, спорядження, історію
особистих зустрічей — і на цьому вирішує, чи цікаво зіграти.

## 9. 💳 Онлайн-оплата

### Провайдер

Для України: **LiqPay (ПриватБанк)**, **Fondy** або **WayForPay** — усі три вміють Apple Pay та
Google Pay і працюють з ФОП. Вибір робиться під реальні умови еквайрингу, а не наперед.

```
payments        id, profile_id, purpose(booking|lesson|tournament|subscription|shop), ref_id,
                amount, currency, provider, provider_id, status(pending|paid|failed|refunded),
                created_at, paid_at
payouts         id, payee_type(club|coach), payee_id, period, amount, status
refunds         payment_id, amount, reason, status, created_at
```

### Важливе правило сторів, яке впливає на архітектуру

Apple і Google дозволяють **зовнішню оплату** (тобто без їхніх 30%) для товарів і послуг реального
світу: оренда корту, урок із тренером, внесок за турнір, фізичне спорядження. Для **цифрових** товарів
— наприклад, преміум-підписки всередині застосунку — обовʼязково їхня внутрішня покупка (IAP) з їхньою
комісією.

Практичний наслідок: усе, що ми плануємо, — реального світу, тобто платимо лише комісію еквайра
(~1.5–2.7%). Але якщо колись зʼявиться «Golden Set Premium» з цифровими перевагами, він мусить іти
через IAP. Ці два потоки не можна змішувати в одному екрані оплати.

## 10. Пропонована послідовність

Усе одразу — це рік роботи до першого користувача, і майже гарантована смерть проєкту від
виснаження. Пропоную порядок, у якому кожен крок дає щось робоче:

| Черга | Що | Чому саме тут |
|---|---|---|
| **1** | Матчі + рейтинг + анкета + статистика | Це ядро й відмінність. Працює без жодного партнера й без грошей. |
| **2** | Пошук партнерів + каталог кортів (без бронювання) | Дає причину користуватись щодня. Корти спершу просто довідник із телефоном клубу. |
| **3** | Турніри + турнірні бали + норма | Замикає рейтингову систему. Оплата участі спершу поза застосунком. |
| **4** | Чати | Має сенс лише коли є з ким і про що говорити. |
| **5** | Бронювання + платежі + абонементи + кешбек | Найдорожчий блок, і він **впирається не в код, а в домовленості з клубами**. Без 3–5 клубів у Хусті чи Києві він марний. |
| **6** | Тренери | Той самий маркетплейс, але потребує ще й перевірки людей. |
| **7** | Магазин | Окремий бізнес. Поки заглушка. |

**Головний ризик усього списку — не технічний.** Бронювання без клубів, тренери без тренерів і
магазин без складу — це порожні екрани. Технічно вони робляться; наповнюються — тільки
домовленостями. Тому черги 1–4 свідомо не залежать від жодного зовнішнього партнера.
